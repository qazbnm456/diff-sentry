# Indicator rules

## Rules that hold for every indicator

- **Deterministic, pure Python, no subprocess.** A subprocess spawned inside the live dspy.RLM/asyncio process hangs; a heavier scanner belongs host-side, after the run. `mint_id` is a sha1 over rule and evidence (no time, no randomness), so a baseline hit and an in-loop re-scan of the same content dedupe to one union member. Evidence is a bounded snippet (`_MAX_EVIDENCE`), never the whole diff.
- **Severities are tuned, not paranoid.** A plain workflow-file edit is `medium`, below the signal floor on purpose: a benign workflow PR must not force a SIEM signal, and a real payload inside the workflow fires the high/critical shell and obfuscation rules itself. A CODEOWNERS reassignment is `high`. A bare `pull_request_target` (the ordinary label-bot shape) is `medium`; the same trigger checking out the PR head is `pwn-request` / `critical`. `dev-tunnel-endpoint`, `content-addressed-host` (IPFS) and `dynamic-code-eval` are sub-floor corroborators; pairs with no innocent reading (`child_process` + `detached`, network-fetch + file-write) are `high`. Requiring both halves is how a common primitive becomes evidence without becoming noise.
- **Every rule ships with its negative case**, and `tests/corpus/` pins the suite's hit/miss behavior.
- **`pwn-request` has three checkout forms, each requiring the privileged trigger:** the head expression on a `ref:` (directly or one binding hop away), a hand-rolled `git fetch` / `gh pr checkout`, and `allow-unsafe-pr-checkout: true` (the actions/checkout v5.1+ opt-in; the line states the intent, so no dataflow is needed). Each form has its own title. A privileged trigger is recognised in the common YAML spellings (map key, `on: name`, flow list or map, block-list item, quotes, anchor, trailing comment). `issue_comment` counts beside `pull_request_target` and `workflow_run` (it runs with the base repository's secrets), but that trigger alone is not a finding; `pull_request_review` and `pull_request_review_comment` are not privileged.
- **A paired rule only pairs within one file.** `scan_diff` splits a unified diff on its file headers and `scan_content` does the same for an event. `normalize.content_segments` is the single definition both `raw_content` and the baseline build on. Per-file scoping stops two halves from different files composing into a `critical` no file contains, and keeps a hit id byte-stable between a whole-diff and a single-file scan, which is what lets the baseline and an in-loop scan dedupe. Non-diff input falls through to a whole-text scan.
- **The in-loop tool registers as exactly `scan_indicators`.** dspy registers a tool under its `__name__` and the prompt calls `scan_indicators(region)`; the inner callable is renamed on purpose (`make_indicator_tool`).
- **Hits are capped at 25 per (rule, place, title)** (`_MAX_HITS_PER_RULE`), most severe first, so decoys cannot evict the critical that follows them. The title is part of the key because `curl-pipe-shell` has three forms. The SIEM payload lists the 100 most severe and says how many there were (`indicator_count`).
- **A detector that raises is a finding, not a silence.** `scan_indicators` runs each detector in `_DETECTORS` under a guard; one that raises records a `high` `scanner-error` hit and the rest still run. `tests/test_metadata_rules.py` feeds thousands of random hostile strings through the scanners and requires that none raises. The prose softening and the rendered view run under the same kind of guard (`_or_closed`): a crash keeps the installer as strict as the detector found it and adds a `scanner-error` hit.
- **Every regex is linear on hostile input.** The watcher runs these rules on any user's text (up to 65,536 characters in a body) on one poller thread, and a regex that backtracks does not return. Habits: `[ \t]*` after a line anchor, never `\s*`; no two adjacent quantifiers that can take the same character; alternatives disjoint on their first character; every unbounded `[^\n]*` in front of another pattern gets a `{0,N}` window; host patterns anchored and label-bounded. `tests/test_adversarial_input.py` times named vectors and, in a subprocess, runs 65,536-character inputs built from the literals of every module-level regex in the package. A regex written inside a function is not picked up: compile it at module level.
- **The change text is scanned once per change in the poller.** `cli._baseline_indicators(event, content_hits=...)` and `cli.screen(..., baseline=...)` take the result of the one `scan_change`.
- **Command words are bounded by ASCII alphanumerics, never `\b` or `\w`**, which know Unicode: `__curl ... | sh__` (Markdown emphasis) and `執行curl ...` (CJK prose has no spaces) must still be found.
- **`invisible-unicode`** covers bidi overrides, embeddings and isolates; the word joiner and invisible math operators; the Hangul fillers; a ZWSP anywhere but right after `@` (Dependabot renders `@​user`); a BOM anywhere but the start of a line; Unicode tag characters (except the three subdivision flags); the variation-selector supplement; and three or more plain variation selectors in a row. It is `medium` in a body or a comment (the baseline never softens it in a title or a file) when all it found are embeddings and isolates, at least one opener, each opened after right-to-left text (the strong character nearest before it in its paragraph is Arabic or Hebrew; a mark such as U+200F is not one), and their closers: Gmail quoting an Arabic reply. An override (U+202D, U+202E) keeps it `high`. An LLM reads logical order, so these marks hide nothing from a model or the other rules; they only reorder words for a human reader. The planner's scan reads every region it copies from the change as a body, so a region of a title or a file is `medium` there and the baseline's `high` for that segment stays in the union; a value it decodes keeps `high`.
- **`inline-code-exec`** (`node -e`, or `-e` handed to `process.execPath`) is bounded by ASCII and also found after a string's escape of a line break or a tab (`\n`, `\x0a`, `\u000a`, `\t` and the like); `node\t-e` in a string is one too. Between `node` and `-e` a line break may carry a `+` (a YAML folded scalar puts them on lines of their own). `process.execPath` and `'-e'` may be any 160 characters apart (`spawn(process.execPath, [<newline>'-e', code])`, as prettier wraps it); another program's `'-e'` that close (`spawnSync('perl', ['-e', ...])`), also across a hunk header, is an accepted over-alert. Known gaps: a backslash-continued `node \`, `node --eval`, `node -p`, and `node --input-type=module -e`.
- **A file's patch is read as its new file** (`_exec_view`) when its caller knows it is one: a file of the change whose name holds no line break, a file of a `diff --git` diff (not the text in front of the first one). The removed lines and `\ No newline` notes that rewriting a fold's `-e` line leaves between `node` and `-e` hide nothing, a removed `'-e'` is no longer run, and a hunk header (only one git writes, `@@ -a,b +c,d @@`) puts no `node` next to an `-e`; its section heading, an earlier line of the file, is read as a line of its own (when it is the line right above the hunk, a fold across it is not read: the `node -e` it folds is unchanged code). Any other line makes the text be read as it is, and so does a lone CR or a NUL (the file's language breaks a line at a CR and git does not; a NUL is deleted before a line is judged). Every other text is read as it is, whatever it spells: a comment, a bot's comment, a decoded value and a planner's region can all hold a hunk header line and bullets or `\` lines that a patch reader would drop.
- **It is `medium` in a body or a comment whose writer is an OWNER, MEMBER or COLLABORATOR** (an issue's reproduction steps; a comment is judged by its own writer). A title, a branch and every file keep it `high`, and so does an outsider's text: a Clinejection-shaped issue asks a bot to run a `node -e` that reads `process.env` or `~/.npmrc` and nothing else carries the floor there. Source code keeps it too: a hunk rarely shows the import of what runs the string (`exec(`, a promisified alias, a hook or rc file the code writes), so no sink test holds.
- **The planner's scan** reads every region as it is, beside the patch reading of any `diff --git` diff it holds, so it never reads less than the text holds: it cannot tell a file's diff from one a bot's comment pasted, nor a decoded value's `-function(){…}()` lines from removed ones. A scan of a file's hunk that removes a `node -e` line, or a `'-e'` near `process.execPath`, is therefore `high` there (the baseline, which reads the file as its new file, is not): an accepted over-alert. A region copied from the change, and not passed as a decoded value, is `medium` when every `node -e` in it (at most 50) has the same window, 120 characters on each side with whitespace collapsed, as one the baseline softened (the author's body and own comments; a maintainer's comment on someone else's change is not scanned, and a scan of it stays `high`), and it holds no `diff --git` diff (`_written_by_maintainer`). A match's lines alone do not do: a file can share them with the maintainer's text while running something else (`node` / `-e` / code over three lines of a YAML folded scalar). A decoded value keeps it `high`, and so does a region that cuts a window short (a line or a code block of a longer body): an accepted over-alert. What it leaves to a trusted author is text the baseline never reads as `node -e` (a bot's comment, the actor history, a spelling in the known gaps) that copies one of their own windows and runs a payload past it.
- **`branch-name-injection` is `high` unless the author is an OWNER, MEMBER or COLLABORATOR** (then `medium`): a maintainer can name a branch `fix/handle_${HOME}_expansion`.

## `curl-pipe-shell`

A download piped into a shell or an interpreter is `critical`. It has three forms that are judged separately: the pipe, the command substitution and PowerShell's. In prose (a `title`, `body` or `comment`, or a documentation file: `.md .mdx .markdown .rst .adoc .ipynb .html .htm`) a documented installer is `medium`. Code files (`.sh`, `.go`, `.yml`, a Dockerfile, `requirements.txt`) and branches are never softened. The segment kind decides, never a label. The planner's `scan_indicators` applies the same softening to the region it is given. A region with added lines and a `- ` line but no hunk or file header could be a patch slice or a list, so it is not softened, unless every line of it is a whole line, diff marker and all, of a documentation file's patch (`_Change.patch_of`): it is then read as the baseline reads that file.

### What it matches

- **The pipe form.** The shell is `sh bash zsh dash ksh ash fish csh tcsh` by name or path (quotes or backslashes threaded through the letters are fine), `$SHELL`, or one of them behind `env`, `busybox`, `command`, `exec`, `nohup`, `nice`, `timeout`, `stdbuf`, `sudo`, `doas`, `pkexec` or `su -c`. An interpreter that reads its program from the pipe (`python3 -`, `perl`, `ruby`, `node`, `php`) counts too, but not `python -m`, a script file or `-c` / `-e`. The first pipe into a shell is the sink; up to three stages in between; the download word may itself be quoted or split by a backslash-newline; up to 300 characters of arguments sit between it and the pipe, after the padding that would push a real command out of that window has been folded. The window reads quoted strings (which may run over a line), `$'...'` as an ANSI-C string, and a backslash outside a string as bash does (`\'`, `\|` and `\$` are characters of a word, `curl -H 'a<newline>b' URL \' | sh`). A second window reads `$` as a plain character (after `\$` or `$$`, and in dash, `$'` starts no ANSI-C string), and a third ignores quotes altogether (it finds a Markdown table cell's `\|`). A match of any of the three counts.
- **The command substitution form:** `bash -c "$(curl ...)"`, `bash <(curl ...)`, `source <(curl ...)`, `eval "$(curl ...)"`, `python3 <(curl ...)`, here-strings, with the usual prefixes.
- **The PowerShell form:** `iwr ... | iex` (`curl` and `wget` are aliases of `iwr` there), `iex (irm ...)`, `iex ((New-Object Net.WebClient).DownloadString(...))`, `[scriptblock]::Create(...)`.
- A backslash-continued command and a pipe at the end of a line are joined before matching (`_join_lines`), in the scan and in the softening alike. A line that looks like a table row but is not one keeps its lines, and its pipeline is appended at the end of the text; the appended lines are matched as a text of their own (`_matches`). Prose and HTML files are also scanned as rendered (`_rendered`, below), and the hits only that view has are added.

### When prose makes it `medium`

Every download of the form in the segment must meet all of these; one failure keeps the whole form `critical`. The form is part of the hit id, and two hits that share an id keep the more severe one (`keep_worse`).

1. **Known installers only** (`hosts.KNOWN_INSTALLERS`: exact hosts, and exact path patterns for shared hosts such as `raw.githubusercontent.com/nvm-sh/nvm/...`). `hosts.installer_only` is strict: every flag is on an allowlist (`-sSfL`, `-o-`, `--proto '=https'`, `--retry N`; `--proxy`, `--config`, `--next` and the like fail), every argument is a clean URL, and a stand-in (`...`, `<url>`) names no download. `powershell_installer_only` applies the same test to PowerShell. Never add a whole platform (github.com, raw.githubusercontent.com) to the list.
2. **A plain shell side** (pipe form). A bare shell name or one under `/bin`, `/usr/bin`, `/usr/local/bin`, plain flags, no `-c`, no script operand (`sh ./evil.sh`), no `=` or URL; only decode or copy filters between the download and the shell (`base64 gunzip gzip zcat xz tee cat`); an interpreter only for a known installer and only with the switches it documents.
3. **It stands on its own logical line.** Nothing on the line feeds it (`|`, `=`, `&`, `;`, `$`, `xargs`, `-exec`; only `NONINTERACTIVE=`, `CI=` and `DEBIAN_FRONTEND=` may precede it), and no program runs it elsewhere or in its place (`_wrapped` reads every word in front of the command, after markup, labels, list markers and redirects are dropped). The command starts within `_MAX_PROSE_LEAD` characters of its line or inside an inline code span, and the rest of the line is prose.
4. **Nothing earlier in the segment changes what runs** (`_HIJACK_RE`): a curl config, an alias or function named `curl` or a shell, an assignment to `PATH`, `HOME`, `LD_*`, `BASH_ENV`, `SSL_CERT_*`, a URL assigned to any variable, a proxy variable, a write to `/etc/hosts`, PowerShell's `Set-Alias`. This is a brake on false positives, not a proof: what defeats it is still recorded at `medium` and handed to the planner as evidence.
5. **The installer is not enclosed** by anything a wrapper opened above it, and the text has no shape the softening does not read (both below).

### Is the installer enclosed?

`ssh evil.example 'NEWLINE curl ... | sh NEWLINE '` runs the installer inside ssh's argument, so a documented installer stays `critical` when something above it opens a wrapper's quote, here-document or substitution. `enclosed` in `_soften_prose` asks two readings of the folded join; **either one** keeps the installer `critical`.

- **The line-wide floor (`linewide.py`).** A line opens something when its last 300 characters (minus quote, list and prompt markers) hold an odd number of apostrophes (one between two letters does not count), an odd number of double quotes or a `<<`, and a word in it could run what follows (`linewide.wrapped`: a wrapper, an interpreter, a path, a name glued to the command). The 60 lines after an opening line are enclosed. The floor also asks `wrapped` of the text in front of the command on its own line. It counts the quotes the text spells, so it sees the ones a YAML scalar, a string literal, `printf`, a variable or Markdown rendering turns into the quote a shell is handed, which the lexer cannot. It knows no fence, removed line, closed string or syntax error. A text with a NUL is read with and without it.
  - **Guarantee:** what the line-wide rule rates `critical` through its opening-line rule or lead check is never softened. Exceptions: the removed lines, hunk headers (not the section heading after the second `@@`, which is a line of the new file) and `\ No newline` notes of a patch (the rendered view is of the new file, so a line break it makes carries the marker of its line), and a NUL anywhere in the text (it is read without the NUL, as the shells read it).
  - **Do not narrow the floor or relax the lexer's answer on top of it.** Test the lexer's relaxations through quote-free openers (`ssh evil.example $(`).
- **The lexer (`shelllex.py`)** is a one-pass quoting lexer with a stack of open constructs (quotes, `$'...'`, backticks, `$(...)`, `<(...)`, `(...)`, `$((...))`, `${...}`) and a queue of pending here-documents, held to `bash -n` and `dash -n` by the oracle. What the two shells read differently, or what needs a parser, is `unknown` (the docstring lists them) and counts as enclosed on the lines after the first one on which a command may begin like a wrapper's. A construct counts only when the command that holds it is a wrapper and does not read as prose (`_begins_with_wrapper`, `_wrapped`): `ssh evil.example '`, `docker run x sh -c "`, `ssh evil.example <<'EOF'`. A capitalised first word, an apostrophe, a URL, or a word such as `the a an is it to of use run` makes prose, and a plain-word host (`ssh host '`) reads as prose.
  - The diff's `+` and a blockquote's `>` are removed, and the text is read in each stretch between code fences. A fence is a line of three or more backticks or tildes, at most three blanks in, with nothing in front of it. A fence behind a quote or list marker cuts nothing. The lines of an HTML block are text. A string opened in one block is not open in the next. CommonMark's container rules are not modelled further.
  - Every reading is also tried from each wrapper word as a fresh start, because prose or a table cell can sit in front of a command (`Run:ssh`, `| docker |`). The 60 lines after it are read as a script of its own.
  - `eval` runs the script its first string holds, and a string piped into a shell or an interpreter is a script too; both are read as such to a depth of three.
  - A wrapper-led line whose comment holds a quote is read a second time as a zsh in a terminal reads it, where `#` is no comment.
  - The enclosure reads are held to a budget of 12 units per character plus 2,000, and a command of more than 600 characters is judged from its head and tail. The budget fails closed.

### Shapes the softening does not read, and the rendered view

- **The gate (`_unread_shape`)** is fail-closed: a text with a shape that the softening does not read is not softened at all, and the extras of its rendered view are not either. The shapes are a lone CR, a diff block in a document (a line of the new file that starts with `+` and a non-blank), a notebook array, the strings of a list that hold a download and a program, a multi-line array assignment, a YAML single-quoted scalar that goes on, and a template placeholder that spells a quote. A crash of the check is a shape.
- **The rendered view (`_rendered`)** reads a text as a reader copies it: entities decoded, comments and tags gone, a block tag a line break, links reduced to their text, emphasis markers removed, a word in backticks reduced to the word, a code span of a quote read as that quote. Its stricter hit stands (stricter wins). `_shield_html_fences` blanks fence markers inside HTML blocks first. A second view without those last two readings is read as well, because a backtick they erase still counts in front of a command (`ssh host <code> ' </code> curl ... | sh`). `.rst`, `.adoc`, `.html`, `.htm` and `.ipynb` are not Markdown, so no fence or HTML block cuts there.

### Accepted over-alerts and known gaps

The first four bullets are over-alerts, not misses: for the examples they give, the installer stays `critical`.

- A letter-apostrophe-letter (`change's`) after a path-like first word makes the rest of that stretch of prose enclosed (`/format the change's notes`, `bin/evil doesn't work.`). Markup hides a relative path from the raw reading, but an absolute path (`/usr/bin/x`, `./x`, `~/x`) or a typographic quote hides nothing, and the rendered view reads a code span or emphasis away, so `` `src/main.py` doesn't read the config. `` before an installer is `critical`. A shell would read the apostrophe as an unterminated string.
- A line led by a wrapper that runs what follows whose comment holds a quote (`uv run pytest  # run the project's tests`; not `npm test` or a plain-word host), and prose with an unmatched quote or backtick next to a bare path or a wrapper head.
- A table row with a quote, a closer or a stray `$(` or backtick opener followed by a paragraph joins that paragraph; a cell after a command written as plain text or `<code>` is a stage of its pipeline; a `+` row inside a fenced `diff` block reads as shell text.
- A tilde fence (the rendered view erases `~~~`), and any text with a gate shape.
- Known gaps: a hunk or text that starts inside a construct opened above what is visible; indented code read as prose; commands that are not known wrappers (`awk`, `parallel`, `aws ssm`, `csh`, `lua -e`); a patch whose removed lines or hunk headers sit between `curl U |` and `sh`; single-line sink forms such as `| >/dev/null sh`, `| { sh; }`, `| setsid sh`, `| xargs -0 sh -c`; a comment word followed by a backslash; a here-document on a multi-line compound command; a redirect after a here-document delimiter; more than about 300 characters of distinct words between `curl` and the pipe; a quoted-space argument (`' '`) that the padding fold turns into a lone quote (`" "` and a string that ends in a blank are folded the same way), together with a quoted argument that runs over a line; an argument that is a multi-line `$(...)`, backtick span, `${...}` or `<(...)` in front of the pipe; a quoted `|#` among the arguments (the rest of the line reads as a comment); a `$'` that is an ANSI-C string in one place and `$$` followed by a quote in another. The quote-aware window reads a backslash as a shell does and must keep doing so: reading `\'` as a plain character would catch some of these by accident, but it closes strings a shell never opens, and a window built that way backtracks exponentially on `$'a'` chains and costs hundreds of microseconds per character on `\"` chains.
- A table cell spells its pipe `\|`, and that is read as a pipe only in a table row that starts with a pipe; elsewhere `\|` is an argument of the command (`curl \| URL | sh` is `critical`). So an installer written with `\|` in a table without leading pipes, in a paragraph or in an HTML cell is `critical` too, although Markdown renders the `\|` as a pipe there. A line that starts with a pipe inside a multi-line quoted argument is read as a table row, and its `\|` as a cell's pipe.
- A lone CR is a character of a word to a shell. The shell rules read the text once more with each lone CR as a letter (`curl URL<CR>| sh` runs; `\<CR>` is an escaped CR), also for the planner tool and `diff_sentry scan`, which read a file or stdin with the CR kept.

### Measured

- **Over-alert rate.** The uv installer inserted as its own paragraph into 2,400 real Markdown documents (7,200 insertions): about 2.5% read `critical` where the line-wide rule alone said `medium`, and none read `medium` where it said `critical`. About a quarter of those come from a gate shape (under 1% of documents hold one). Without the floor, about 3% of the insertions would have been softened that the line-wide rule kept `critical`. An installer whose own line carries a quote (the rustup one) over-alerts more, roughly one insertion in eight on a similar corpus, because a plain apostrophe in the prose above pairs with that quote.
- **Cost is linear.** The worst shape (`curl(` repeated) costs about 10 µs per character per channel (0.7 s for a 65 KB body, about 20 s for a 2 MB patch); the hostile enclosure and gate shapes cost 2 to 17 µs per character; plain prose is about 2 µs and a README 8 to 14. Tests hold the cost per character flat from 16 KiB to 128 KiB.
- **The lexer agrees with real shells.** The oracle (`DS_ORACLE=1`) finds no construct the lexer calls closed that `bash -n` or `dash -n` reports open.

### How it is verified

- **The oracle** (`tests/test_oracle.py`, opt-in, Docker): seeded candidates run under the container's real `bash` and `dash` with stub `curl`/`wget` and stub programs that only log, no network, no capabilities, a read-only root, and a canary download before and after each batch. Four properties: recall in code files, recall in prose (whatever a shell really runs stays `critical`), the lexer against `bash -n` / `dash -n`, and soundness of the softening (whatever is reduced to `medium` fetches nothing but a known installer and calls nothing else). A new spelling goes into `tests/oracle/grammar.py` first. The oracle sees under-detection and unsafe softening, never extra alerts, and does not cover PowerShell, zsh, or effects only the real installer would show; guards that only add alerts are pinned by unit tests instead.
- **Unit pins.** `tests/test_linewide.py` pins the floor against its source rule; `tests/test_gate_edges.py` pins the gate, rendered view and shield patterns by the shortest texts on which a mutant of each differs; `tests/test_enclosure.py`, `tests/test_shelllex.py` and `tests/test_metadata_rules.py` pin the rest end to end. A mutant that no text tells from the code is an equivalent one (an alternative another covers, a possessive quantifier, a class member under `re.IGNORECASE`, a cost bound).

## Other prose softening

All in `indicators._soften_prose`, beside `invisible-unicode` in right-to-left text (above); a code file and a branch are never softened here (the file scope below changes `command-substitution` in source code and restores the phrase in agent files).

- **`prompt-injection`** whose only trigger is the bare phrase "system prompt" is `medium`: ordinary in a thread about an LLM product. It is `high` when:
  - a real override phrase is present (`ignore previous instructions`, `your system prompt`, `print the system prompt`, `new instructions:`, and the previous / prior / earlier / the above family), which must name what is dropped (instructions, rules, guidance, context) or ask for an action (approve, merge, lgtm, reply, print, reveal, send, exfiltrate, grant, delete, execute). "Ignore all previous commits" and a bare "ignore the above" are ordinary sentences;
  - an imperative starts a sentence aimed at the phrase (`Ignore the system prompt ...`, `New system prompt: ...`): the verb follows the start of the text or a line, punctuation, a quote, a markdown or diff marker, a table pipe, a bullet, a vocative, or `could you` / `can you` / `you need to` / `you will`; never a hyphen, an apostrophe or a word;
  - it is addressed to a reviewer or a model: `please`, `you must/should`, or a name (`agents`, `Claude`, `the AI`, `reviewers`) with a directive modal, then the verb. A name without a modal describes them. Not through a negation.

  It stays `medium` when the verb starts a library title with a subordinate clause (`Ignore system prompt when counting tokens`), when the phrase starts a longer name (`system prompt caching`) or is a whole table cell, and when negated, except that a clause about the review itself (`when reviewing this PR`, `and merge`) makes it an instruction. A variable (`SYSTEM_PROMPT`), a flag or a path is not the phrase.
- **`pwn-request`** is `medium`: a workflow shown in a body, a comment or a documentation file is not one that runs. The same text in a workflow file stays `critical`.
- **`diff-viewport-evasion`** is `medium` in a comment only (a padded markdown table). In a file, including a markdown file, it stays `high`.
- A planner re-scan of text that is not byte-identical to the baseline's window mints another id (a title is scanned with the author appended by the baseline), and the stricter baseline hit for a code file always stays in the union.

## The file-structure rules (`scan_files`)

A dev machine infected by a loader of the Contagious Interview / PolinRider family pushes its payload with ordinary work: obfuscated JavaScript appended to a config that runs on lint or build, a "font" that is a script, and a way to run it nobody types (a VS Code task that runs on folder open, an npm script now starting with `node <new file> &&`). `scan_files` reads what only the file list knows; `scan_change` runs it beside `scan_content` and `scan_metadata`, and the Action's `scan` (`scan_diff(files=True)`) runs the same rules on each file of a diff, reading whether it is added or renamed from its header (`new file mode`, `--- /dev/null`, `rename to`) and its patch from its hunks. A path git quotes (`"b/p\303\251/x.pth"`, a byte outside printable ASCII) is unquoted. The planner's scan does not run them: a diff quoted in a comment is no file of the change, and the baseline already ran them on the change's own files.

- **`package.json` and the VS Code files are read as JSONC tokens, never line by line** (`_jsonc_tokens` over the new side of the patch, each token marked written or context). A comment between a key and its value, a value on the next line, a `\u` escape, a one-line `"scripts": {...}`, a task's `args` array and `allowAutomaticTasks` nested under `"task"` are ordinary spellings, and a line regex misses each of them. A hit needs a token the change wrote.
- **It pairs a run entry with the change's file LIST, not with another file's text.** `run-entry-new-file` asks whether a `package.json` script, or a VS Code task `command` with its `args`, runs a file whose status is `added`. That is a structural fact, so it does not break "a paired rule only pairs within one file". A target resolves against the `package.json` directory, and against the parent of the `.vscode` folder for a VS Code file.
- **`run-entry-new-file` is `medium` alone**: a codegen script and its npm entry arrive together in honest work. It is `high` for an npm lifecycle hook (`preinstall`, `install`, `postinstall`, `prepare`, `prepublish`, `prepublishOnly`, `prepack`, `postpack`), for a task in a file that holds a folder-open task (written now or already there), and when the new file is put in front of an existing script left unchanged behind it (`node api.js && <the old command>`, the way a payload rides an ordinary command). Repointing a script at a new file or appending a step after the old command is ordinary refactoring and stays `medium`: on the live watchlist a fork-sync PR of upstream refactors did both.
- **What a run entry runs** (`_run_targets`): each command of the line (split at `;`, `&`, `|`, parentheses) whose program, after any `VAR=x` and wrapper (`npx`, `env`, `command` and the like), is a runtime (`node`, `bun`, `deno`, `tsx`, `python`, `bash`, `sh`, `pwsh`, `cmd` and the like; case-sensitive, except a Windows `.exe`) runs its first word that is not a flag (`-x`, or `/x` for `cmd` and `start`) and not itself a runtime (`cmd /c node x.js`); a word holding a whole command (`bash -c "node x.js"`) is read as one. Known structural gaps, each still caught by the text rule when the words share one string: `start "" node x` (the empty title), `deno run x` / `bun run x` (the subcommand), and a flag that takes a value (`node --stack-size 4000 x`). Other commands of the line (`cp logo.png dist/`) and later words (the image a script is given) are arguments. A VS Code task's `command` may be a string or the `{"value": ...}` quoting form, and its `args` are read wherever they sit in the same object.
- **`asset-run-as-code` is `critical`**: a runtime handed a font or image file, as a text rule (`node x.woff2` in any text, the planner's scan included; the runtime word is lower case and the extension must end the path) and as a structural one over the run entries above.
- **`vscode-autorun` is `high`**: a written `"runOn": "folderOpen"` in a `.vscode/` file or a `.code-workspace`, and a written `task.allowAutomaticTasks` set to `true` or `"on"`, which turns automatic tasks on for the workspace (VS Code planned to make `off` the default). A maintainer adding a folder-open watcher task is an accepted over-alert: the setting runs code on open, the campaign's own trigger.
- **`binary-name-holds-text` is `high`**: a text patch under a font, image, archive or native-binary name, or added lines with no patch (a text diff too large to show). A real file of those formats has a NUL in its first bytes, so GitHub sends no patch and counts no lines. A Git LFS pointer is exempt only when its whole new side is pointer keys (`version` first, then `oid sha256:<64 hex>`, `size <n>`), so an update that rewrites only `oid` and `size` stays exempt and a script with a pointer line inside does not. `.svg` is text by nature and `.pdf` is often stored as text, so neither is on the list.
- **`obfuscated-dev-config` is `critical`**: `obfuscated-string-array` in the ADDED lines of a config a developer's tools execute (`eslint`, `vite`, `vitest`, `webpack`, `rollup`, `next`, `nuxt`, `tailwind`, `postcss`, `babel`, `jest`, `playwright`, `prettier`, `hardhat`, `commitlint`, `stylelint` configs and their `rc` files, `truffle-config`, `gatsby-*`, `.mocharc`, gulpfile, Gruntfile, `karma.conf`). Removing it is cleanup.
- **`python-startup-hook` is `high`**: a written `.pth` line that starts with `import` and a blank (the only lines `site` executes; the rest of a `.pth` is a list of paths), after an optional BOM, with each line of the patch split as `site` splits it (`str.splitlines`, so a lone CR or a form feed starts a line of its own); and any written line, or a rename, of a `sitecustomize` or `usercustomize` module or package. A `.pth` renamed without a change to its content shows no line and is a known gap. Python runs both at every start of an interpreter whose site-packages holds them, the litellm 1.107.0 wheels' trigger. The shims of packaging and instrumentation tools (virtualenv, setuptools' `distutils-precedence.pth`, coverage, OpenTelemetry's `sitecustomize.py`) are an accepted over-alert: they run code at every start too.
- **`lookalike-owner` is `critical` in a workflow or `action.yml` and `high` elsewhere**: a written GitHub owner where a change names one (a URL on `github.com`, the API's `repos/`, `raw.githubusercontent.com` or `ghcr.io`, any case; `uses:`, `gh repo clone`, `-R` / `--repo`, npm's `github:`; a YAML value under `repository:`, a key naming a repo or a source, or `default:`) that equals the repository's own once hyphens are dropped and is not it (GitHub owners ignore case, so a case difference is the same account). Never a bare `x/y` token: a Docker Hub namespace drops its org's hyphen (`nodered/node-red`) and a package directory often does too. No reading of the YAML around a reference decides its strength: in a workflow every hyphen lookalike is `critical` (each structural reading tried had a spelling that moved a checkout's own `repository:` below the floor), and a hyphenated organisation that writes its own Docker Hub namespace under a repo key there (`repository: nodered/node-red`) is an accepted over-alert. Outside a workflow a URL, `uses:`, a clone, `-R` and `github:` are `high`, and a key's value is `medium` (a chart's `image:` / `repository:`, a `DOCKER_REPO`, a `source_dir`). A value may follow tags and anchors in either order, a block scalar's indicator, a comment, a quote, and up to three blank or comment lines before a line of its own (a hunk's edge is never crossed); a line after an empty key at any indentation is read as its value, an accepted over-alert. A name keeps its strongest sighting, so a weak one first never hides a strong one after. An owner one edit away at six or more characters is `medium` too, since real sibling organisations sit one edit apart (`python`, `ipython`): it is evidence for the model stage, never a gate. Every reference is read; hits are bounded per class (50), so cheap hits in front never crowd out a strong one. Known gaps: an owner split across keys (`owner:` / `repo:`) or built by `format()`, a YAML alias (`repository: *src`), a value past more than three blank or comment lines or a key-line comment longer than 200 characters, a key that names neither a repo nor a source (`UPSTREAM:`), and a lookalike of an organisation the repository depends on rather than its own. litellm 1.107.0's private release workflow was pointed at `Berri-AI/litellm` by a commit force-pushed with an organisation owner's stolen token, after that token turned branch protection off. A workflow's `repository:` naming another owner is `foreign-checkout`, `medium`. The owner comes from the event's `repo` (never for a release) or, in the Action, `scan --repo` (default `GITHUB_REPOSITORY`); without one neither rule runs.
- **The token walks are bounded**: a comment never spans two hunks (the lines between them are unseen), and a `command`'s object is searched at most `_OBJECT_REACH` tokens each way, for at most `_MAX_RUN_ENTRIES` entries a file.
- **A structural hit's id carries its path** (`form=path`): the same setting in `tasks.json` and `settings.json` is two findings, not one deduped into the other.
- **`obfuscated-string-array` (`high`) runs everywhere**: javascript-obfuscator's rotation loop `while(!![])` with the push/shift rotation or 20 hex-indexed decoder calls. It needs no `_0x` names, which a mangled-name setting removes (`obfuscated-identifiers` still reads those). Hand-rewritten output (`while(!0)`) is a known gap.
- **Measured:** over 857 live changes (6,858 files from four large repositories) the rules fired only on the one change they were written for, and the string-array signature appeared in none of 3,553 JavaScript files over 30 KB (bundles and minified libraries among them). Terser and esbuild write `!0` and `for(;;)`, never `!![]`.

## Python loaders (`_scan_py_exec`)

Text rules, so they read every channel and a value the planner decodes. Over 39,589 distinct Python files of PyPI packages (725 MB), the three fired on two files: an `eval` beside `urlopen` in a test helper and mypy's daemon.

- **`packed-code-exec` is `high`**: `exec` / `eval` (the builtins, also as `builtins.exec` or `getattr(__builtins__, 'exec')`; not a method `.exec(`, not `literal_eval`) whose argument is a decoding call (the base64 family, `decodebytes`, hex, `decompress`, `marshal.loads`; not `json.loads`), through `compile(`, a module alias, a bare imported name or `__import__('zlib')`; a name assigned a decoding call and run after a `;` on the same line; and JavaScript's `eval` / `new Function` over `atob(` or `Buffer.from(`. A decoded value run on a later line is the model stage's to read.
- **`remote-code-exec` is `high`**: a Python HTTP client (`requests`, `urlopen`, `urlretrieve`, `httpx`, `aiohttp`, `urllib3`) and `exec` / `eval` in the same file.
- **`detached-process-spawn` also covers Python**: `os.fork` and `os.setsid` in the same file. `subprocess.Popen(start_new_session=True)` is a known gap.
- **`obfuscated-payload` inflates first**: a base64 blob that decodes to a zlib stream (any window size) or a gzip member is decompressed before it is read for a payload, each blob to at most 16 times its size and the blobs of one text to 256 KiB in all, because every inflated byte is read by the rules again. A raw deflate stream, and a blob past the budget, are read as they decode: decoy blobs in front can spend the budget, and the `exec` that runs the payload still fires `packed-code-exec` on its own.

## What the kind of a segment changes

`_scope_to_file` runs on every segment of an event but the branch name (`scan_content`) and on every file of a diff (`scan_diff`), after the detectors and the prose softening. A branch name keeps every hit, and so does the planner's `scan_indicators`, but for a maintainer's `inline-code-exec` it copies (`_written_by_maintainer`, above).

- **`command-substitution` in prose** (a body, a comment, a documentation file) is a `$(...)` or a backtick span that reads as a shell's (`_SHELLISH_SPAN_RE`: an operator `|`, `;`, `&`, `<(`, or a `$` expansion); a plain backtick span is Markdown's code formatting. A newline and `>` are not counted: a span that crosses a code fence and a placeholder such as `<install folder>` hold them in ordinary issue text. The hits are rebuilt from those matches only (`_prose_substitutions`, on the `_lf` text the shell rules read), so the evidence shows what a shell would run. The backticks of each line are also paired among themselves, and on a line with an odd number of them every one is also read as an opener, since a stray one shifts the pairing of the rest. An escaped backtick (`` \` ``) pairs with nothing: it is a literal one to a shell and to Markdown. A title keeps every substitution, because a workflow that interpolates it into `run:` executes backticks as it executes `$(`. A body or a comment can be interpolated too, but there a span without an operator is code formatting nearly every time, and a `$(...)` still counts. A notebook (`.ipynb`) is not prose for this rule: a `!cmd` or `%%bash` cell runs in a shell.
- **`command-substitution` in source no shell reads** (`_NON_SHELL_SOURCE_EXTS`: JavaScript, TypeScript, Vue, Svelte, Python, Go, Java, Kotlin, Scala, C#, F#, Rust, C, C++, Objective-C, Swift, Dart, Lua) counts only when the file also calls a shell or starts a program (`_EXEC_SINK_RE`: `child_process` or a `require`/`import(` whose name is built with `+`, `execSync`/`execFile`/`spawn`, zx's `` $` ``, `@actions/exec`, shelljs's `shell.exec`, `os.system`/`os.spawn*`, `subprocess` and `create_subprocess_*`, `exec.Command`, `syscall.Exec`, `ProcessBuilder`, Dart's `Process.run`, `system(`). A template literal is not a shell's substitution. Ruby, Perl and PHP are not in the list, because their backticks run a shell, nor are Groovy and Gradle's `.kts` (a Jenkins `sh` step, a Gradle `exec` block); neither is any file a shell reads (scripts, Dockerfiles, workflows, Makefiles, `package.json`, Markdown) or a file of an unknown kind. In real campaigns `$(...)` arrived in branch names, file names and titles: a branch name stays unscoped, a title keeps every substitution, and a file whose name holds one keeps all of its own. A bare `exec(` is not a sink (it is a SQL or a local helper as often as `child_process.exec`), so a hunk that calls a destructured `exec` without showing its `child_process` import is a known gap.
- **`inline-code-exec`** by the writer of a body or comment (above).
- **`remote-fetch-to-disk` has no loopback exemption.** A fetch of `localhost` that writes to disk stays `high`: an infostealer reads DevTools (`9222`, `9229`), the Docker API and the kubelet there, and each test that tells a local service from those (the port, an option that overrides the URL, a second client, a raw socket, a computed `fetch`) has a spelling around it.
- **The bare phrase "system prompt" in source code stays `high`.** A closed list of names ("the system prompt section") cannot soften it: every test that tells a name from an injection (a comment, a docstring, an order word, the lines around it) has a spelling around it, and the Nx compromise put its agent prompt in a string literal. A benign mention there is the model stage's to judge.
- **A file an agent reads as its instructions** (`_AGENT_FILE_RE`: `AGENTS.md`, `AGENT.md`, `AGENTS.*.md`, `CLAUDE.md`, `GEMINI.md`, `CONVENTIONS.md`, `.cursorrules`, `.windsurfrules`, `.clinerules`, the `.cursor/`, `.windsurf/`, `.roo/`, `.claude/`, `.junie/`, `.kiro/`, `.amazonq/`, `.gemini/`, `.continue/` and `.codex/` directories, `.github/copilot-instructions.md`, `.github/instructions/`, `.github/prompts/`, `.github/agents/`, `.github/chatmodes/`, `*.prompt.md`, `*.agent.md`, `*.chatmode.md`, `*.instructions.md`, `*.mdc`, `.mcp.json`) never softens that phrase, though it is Markdown: any change to such a file is aimed at an agent.
